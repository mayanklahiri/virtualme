## 1. Marvin release notes

1. **Artifact**: every release requires a committed notes file `release-notes/vX.Y.Z.md` present at the tagged commit. Content contract:
   - Front section: 3–8 bullet points covering only things a **user** cares about, grouped when applicable under bold lead-ins `**New**`, `**Security**`, `**Reliability**`, `**Performance**`. Each bullet: what changed and why the user should care, one to two sentences.
   - Written in the voice of **"Marvin the Release Bot"**: a brilliant, deeply weary, dryly resigned robot who finds the whole business of releasing software faintly beneath him but does it flawlessly anyway. Tone markers: understatement, sighing precision, reluctant competence ("I have queued your jobs. They will run. Joy."), zero exclamation marks.
   - **Absolute prohibition**: no character names, place names, plot elements, quotations, numbers-as-references, or any other identifiable material from the source of the archetype. Tone only. The `/do-release` skill (§4) includes a self-check step enumerating this prohibition before committing notes.
   - Footer line (fixed): `— Marvin, Release Bot. The commit list below is generated by machines with less personality.`
2. **Workflow enforcement** (`.github/workflows/release.yml`):
   - `verify` job gains a step after the npm immutability check:

```yaml
      - name: Release notes present
        run: test -s "release-notes/$GITHUB_REF_NAME.md" || { echo "missing release-notes/$GITHUB_REF_NAME.md" >&2; exit 1; }
```

   - `github-release` job: replace `--generate-notes` with

```yaml
          gh release create "$GITHUB_REF_NAME" \
            --verify-tag \
            --title "$GITHUB_REF_NAME" \
            --notes-file "release-notes/$GITHUB_REF_NAME.md"
          gh release edit "$GITHUB_REF_NAME" --notes "$(cat "release-notes/$GITHUB_REF_NAME.md"; echo; echo '---'; gh api "repos/$GITHUB_REPOSITORY/releases/generate-notes" -f tag_name="$GITHUB_REF_NAME" --jq .body)"
```

     (Create with curated notes, then append the auto-generated commit list below a rule via the generate-notes API. If the two-step edit proves flaky, an acceptable fallback is curated-notes-only; note whichever shipped in the commit message.)
3. `release-notes/` is a normal committed directory; add `release-notes/README.md` (two lines: naming convention, "authored by /do-release").

## 2. Docker Hub repository overview and metadata

1. **`docker/DOCKERHUB.md`** — the overview shown on `hub.docker.com/r/mayanklahiri/virtualme`. Verbatim content:

```markdown
# Virtual Me

A private background agent that runs entirely on your machine: local LLM,
real browser on a virtual desktop, speech, and outbound mail. No cloud, no
accounts, no telemetry.

## Run it

    npx virtualme start

or with plain Docker:

    docker run -d --name virtualme -p 8080:8080 \
      -v ~/.virtualme:/home/virtualme/.virtualme \
      mayanklahiri/virtualme:latest

Then open http://localhost:8080 in a browser on the same network.

Your data (browser profile, chat history, projects, mail queue) lives in
`~/.virtualme` on the host and survives updates.

## Good to know

- Needs about 8 GB of RAM; the local model alone uses ~4 GB.
- First start is slow while the model loads. Give it a few minutes.
- Prototype trust model: no auth or TLS. Run it on a trusted private network only.

Source, docs, and issues: https://github.com/mayanklahiri/virtualme
```

2. **Automated push**: new step in the `docker-manifest` job (after the manifest create, same job so it only runs when images actually published), using the Docker Hub API directly (no third-party action, keeping the workflow auditable):

```yaml
      - name: Update Docker Hub overview
        run: |
          TOKEN=$(curl -fsS -H 'Content-Type: application/json' \
            -d '{"username":"'"${{ secrets.DOCKERHUB_USERNAME }}"'","password":"'"${{ secrets.DOCKERHUB_TOKEN }}"'"}' \
            https://hub.docker.com/v2/users/login/ | jq -r .token)
          jq -n --rawfile body docker/DOCKERHUB.md \
            '{full_description:$body, description:"Private local background agent: local LLM, virtual browser, speech, mail. No cloud."}' \
          | curl -fsS -X PATCH -H "Authorization: JWT $TOKEN" -H 'Content-Type: application/json' \
              -d @- "https://hub.docker.com/v2/repositories/$IMAGE/"
```

   Requires `actions/checkout` in that job (add it) and the `DOCKERHUB_TOKEN` to be a password or PAT with write scope (document in the README runbook; if the current token is read-only the maintainer must reissue — the workflow step failing with 403 must fail the job loudly, not silently).
3. **Docker Hub short description** is set by the same PATCH (`description` field, ≤100 chars, kept in the step above).

## 4. The `/do-release` skill

New skill `.cursor/skills/do-release/SKILL.md` (symlinked tree at `.claude/skills` picks it up automatically). Frontmatter description: `Execute a full npm + Docker release: preflight, Marvin release notes, version bump, tag, watch CI, verify all channels.` Body is a numbered procedure the agent follows literally:

1. **Preflight**: working tree clean on `main`; `npm run check` green; `gh auth status` OK; secrets exist (`gh secret list` shows `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `NPM_TOKEN`); run the §3.1 `gh repo edit` command (idempotent); confirm `docker/DOCKERHUB.md` exists and mentions the current major features (if stale, update it in this release's commit).
2. **Version**: decide semver bump from the change set since the last tag (`git describe --tags --abbrev=0`; `git log <last>..HEAD --oneline`); edit `package.json` version (no `npm version` — no tag yet).
3. **Marvin notes**: draft `release-notes/vX.Y.Z.md` per spec 025 §1 from the git log and any specs executed since the last tag, sorting bullets into New/Security/Reliability/Performance; **self-check**: re-read the draft and confirm the tone-only rule (no names, places, quotes, plot, or numbers from the source archetype); include the fixed footer line.
4. **Commit**: single commit `release: vX.Y.Z` containing the version bump + notes (+ any DOCKERHUB.md refresh).
5. **Tag and push**: `git tag vX.Y.Z && git push origin main --tags`.
6. **Watch**: `gh run watch` the `release` workflow to completion; on a failed job, follow spec 004 §"failure modes" (re-run failed jobs for the same attempt; a burnt version number is bumped, never reused).
7. **Verify all channels**: Docker Hub shows `X.Y.Z`, `X.Y.Z-amd64`, `X.Y.Z-arm64`, moved `latest`, and the refreshed overview text; `npm view virtualme@X.Y.Z` resolves and npmjs.com renders the readme; the GitHub Release page shows the Marvin notes with the generated commit list appended.
8. **Report**: summarize versions, links, and anything skipped.

Register the skill in `AGENTS.md`'s Skills table and the README skills table during the docs pass.
