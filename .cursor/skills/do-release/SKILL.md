# /do-release — full release

Follow this procedure literally. Stop immediately when any step fails.

1. **Preflight**
   - Confirm the working tree is clean and checked out on `main`.
   - Run `npm run check`.
   - Run `gh auth status`.
   - Run `gh secret list` and confirm `DOCKERHUB_USERNAME`,
     `DOCKERHUB_TOKEN`, and `NPM_TOKEN` exist.
   - Apply the repository metadata idempotently:

         gh repo edit mayanklahiri/virtualme \
           --description "Private local background agent: local LLM, virtual browser on a virtual desktop, speech, and mail. Zero-dependency CLI, single Docker image." \
           --homepage "https://hub.docker.com/r/mayanklahiri/virtualme" \
           --add-topic agent --add-topic local-llm --add-topic docker --add-topic automation \
           --add-topic self-hosted --add-topic llama-cpp --add-topic browser-automation --add-topic privacy

   - Confirm `docker/DOCKERHUB.md` exists and mentions the current major
     features. If stale, update it in this release's commit.

2. **Version**
   - Find the last release with `git describe --tags --abbrev=0`.
   - Review the change set with `git log <last>..HEAD --oneline`.
   - Decide the semantic-version bump from that change set.
   - Edit `package.json` version directly. Do not run `npm version`; the tag
     does not exist yet.

3. **Marvin notes**
   - Draft `release-notes/vX.Y.Z.md` from the git log and any specs executed
     since the last tag.
   - Write 3–8 user-facing bullets, grouped where applicable under bold
     lead-ins `**New**`, `**Security**`, `**Reliability**`, and
     `**Performance**`. Each bullet says what changed and why a user should
     care in one or two sentences.
   - Use Marvin's brilliant, deeply weary, dryly resigned voice: understated,
     sighingly precise, and reluctantly competent. Use zero exclamation marks.
   - Self-check: re-read the draft and confirm the tone-only rule (no names,
     places, quotes, plot, or numbers from the source archetype).
   - End with exactly:

         — Marvin, Release Bot. The commit list below is generated by machines with less personality.

4. **Commit**
   - Make one commit named `release: vX.Y.Z` containing the `package.json`
     version bump, release notes, and any `docker/DOCKERHUB.md` refresh.

5. **Tag and push**
   - Run `git tag vX.Y.Z && git push origin main --tags`.

6. **Watch**
   - Run `gh run watch` for the `release` workflow through completion.
   - On failure, follow spec 004's failure modes: re-run failed jobs for the
     same attempt. A burnt version number is bumped and never reused.

7. **Verify all channels**
   - Confirm Docker Hub has `X.Y.Z`, `X.Y.Z-amd64`, `X.Y.Z-arm64`, and moved
     `latest`, and displays the refreshed overview.
   - Confirm `npm view virtualme@X.Y.Z` resolves and npmjs.com renders the
     repository README.
   - Confirm the GitHub Release page shows the Marvin notes followed by the
     generated commit list.

8. **Report**
   - Summarize the released versions and links, and identify anything skipped.
